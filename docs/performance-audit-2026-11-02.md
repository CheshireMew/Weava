# 性能审查：2026-11-02

当前最需要处理的是发布流程占用网站主进程，其次是统计报表的计算量、后台资源的缓存，以及不断增长的任务记录。项目已经有发布对象复用、发布快照缓存、数据库列表索引、媒体流式响应和后台任务隔离，因此没有必要整体更换技术栈。问题主要在于部分入口仍然直接执行重计算，以及已有计算结果没有被充分复用。

## 优化清单

P1 表示会影响整站响应或主要发布流程，应优先处理；P2 表示有明确的资源浪费或增长问题；P3 表示场景性优化，实施前应补充对应测量。以下编号按问题来源归并，避免把同一根因重复计数。

**1. P1：发布预览在网站主进程中重复进行全站准备，单篇发布也没有限制计算范围。已实测。**

`apps/web/src/api/publication.ts:21` 先调用 `previewPublication()`，随后又调用 `preparePublication()`。前者本身已经执行准备。`packages/core/src/publication.ts:35` 每次读取全部工作稿，`:60` 深复制全部公开内容，`:176` 渲染校验每篇文章，`:211` 再复制一次用于计算变化。`packages/core/src/render.ts:231` 又为每篇内容调用 `recommendedEntries()`；该方法在 `editorial.ts:37` 扫描并排序全站候选，形成接近按文章数量平方增长的重复工作。已经保存的 `entry.html` 也没有阻止重新渲染正文。最终写入时 `publication-store.ts:49` 还会为全部文章重新计算对象散列和搜索文本；数据库里复用了相同对象，并不意味着免去了这些计算。

仅将第二次调用删掉只能减少一部分耗时。完整处理应当把准备、摘要和扩展校验统一交给受管理的发布任务，产出一个固定修订、带基准版本和依赖指纹的候选对象，预览读取同一候选的摘要，提交复用该候选并再次核对版本。把内容自身、共享布局、设置、引用关系和推荐数据的依赖记录清楚，按依赖变化决定哪些派生结果需要重算；推荐候选和排序数据按公开版本建立索引，避免每篇文章重复构造全站数据。最终提交只承担必要的数据库写入和公开指针切换，继续保留冲突检查和原子性。

**2. P1：定时发布仍然直接运行在网站进程，并把耗时准备放入写事务。代码路径已确认。**

`apps/web/src/runtime.ts:57` 的定时器调用 `runSchedulesAsync(site, ...)`。`packages/core/src/schedules.ts:91` 起的流程做两次准备，随后 `runSchedules()` 在 `:60` 起的写事务内调用 `site.publish()`，再次准备并提交。发布计划的 `publication-plans.ts:33` 和 `:57` 也有同样结构；安排定时发布和保存计划本身同样在事务里调用预览。声明 `async` 不会让这些同步计算离开主线程。

因此，已有发布任务子进程不能覆盖这些入口。到期检查应当只读取到期计划并入队，让手动、定时、计划发布复用同一套受管理执行流程。任务领取、指定修订、计划完成和公开版本切换的原子保证需要保留；耗时准备移到事务外，短事务内重新检查状态并提交。基于第 1 项测量可以确认这一代码路径具有长时间占用主线程的风险，但本次没有额外模拟真实定时到点的 HTTP 并发延迟。

**3. P2：维护和引用信息接口在主进程扫描完整历史。已实测。**

`apps/web/src/api/media.ts:37` 直接调用 `mediaReferences()`。`packages/core/src/media.ts:83` 把全部文章历史一次读进内存，再解析 JSON 和提取引用。`apps/web/src/api/operations.ts:88` 的空间使用查询直接调用 `storageUsage()`，后者在 `maintenance.ts:10` 起扫描当前记录、全部修订、公开对象和历史归档，并同步遍历媒体和备份目录。归档预览 `operations.ts:91` 也在主进程展开多个公开版本。

10,000 个修订时已经分别占用约 133 ms 和 111 ms；文章更新越多，查询越慢，即使只查看一个从未被引用的附件也一样。应为当前内容、公开版本和历史修订维护引用索引，并把完整盘点、归档计划计算放到现有任务系统。页面读取带扫描时间和数据版本的结果快照，避免点开信息面板就重新扫描磁盘和数据库。

**4. P2：带哈希的后台资源禁止缓存，而且每次重新读取和压缩。代码与文件体积已确认。**

`apps/web/src/middleware.ts:48` 到 `:62` 对 `/_admin/assets/` 的 JS/CSS 和后台 HTML 一律使用 `no-store`，同时 `readFileSync()` 读取完整文件。后面的压缩逻辑又对相同资源逐请求 gzip。管理后台已有独立编辑器及统计分块，但再次打开、刷新或切换到之前加载过的模块时，仍会重复付出资源传输成本。

带构建哈希的静态资源应使用长期缓存和 immutable；后台 HTML 继续采用适合登录态的策略。预压缩结果随程序版本保存，或者为不可变资源建立有容量上限的压缩缓存。若前面有静态服务，也可以由它负责这些文件，重点是要验证实际响应头，而不只是修改 Vite 配置。静态资源中没有用户数据，不需要因后台登录态而全部禁止缓存。

**5. P2：媒体要求每次校验，却没有实现条件响应。已用真实响应函数验证。**

`middleware.ts:74` 给公开媒体设置 `public, max-age=0, must-revalidate`，但 `packages/core/src/media-response.ts:6` 只有文件状态、Range 和 HEAD 处理，没有 ETag、Last-Modified 或 304 分支。这意味着浏览器重复访问会重新取得完整媒体内容。流式读取控制了服务端内存，却没有省掉重复下载。

根据媒体身份和实际可变性选择策略：内容散列文件可长期缓存；可变来源路径使用 ETag/Last-Modified 和条件请求。需要同时处理 Range、If-Range、HEAD，并且每次先执行现有媒体访问判断，再决定能否返回缓存响应。私有媒体策略继续按私有内容处理，不能直接把所有 `/media/` 都设成公开 immutable。

**6. P2：统计报表按明细重算多组结果，窄时间范围也会计算全历史。已实测。**

`packages/core/src/analytics-reports.ts:155` 将所选期和对比期事件联表后全部读取；`:159` 再读取相关会话明细。后续反复生成数组、Map、Set 并按时区转换每条事件；`:411` 计算八组概览，`:424` 计算全历史去重统计。筛选路径和维度的一部分工作发生在读取之后。10 万事件的 30 天报表达 11.1 秒，单日范围仍接近 1 秒。

`apps/web/src/api/analytics.ts` 已通过 `TaskResults` 在子进程计算，并有 10 秒缓存及并发合并，因此这里的主要问题是等待时间、工作进程内存和任务槽位，不应误报为报表计算直接阻塞网站主线程。完整方案应保留可回溯明细，建立会话首次来源、按日汇总及相关维度索引，让概览、生命周期指标和所选范围分开读取、分开缓存。涉及跨日的访客/会话去重不能简单把每日独立访客相加。高基数明细提供数据库分页，筛选尽可能下推到查询层；旧导入数据也要有一致的增量重建策略。

100,000 条事件组的进程 RSS 最后为 870.4 MiB、堆使用约 625.4 MiB，只是连续调用后的快照。任务子进程设置了 `--max-old-space-size=768`，更大数据集有接近堆上限的风险，但本次没有复现生产任务 OOM，也没有把快照写成峰值。

**7. P2：实时查询使用一次性持久任务，任务历史又让高频调度逐渐变慢。已测量并核查查询计划。**

`apps/admin/src/analytics/useAnalyticsReport.ts` 在可见页面每 15 秒请求实时统计；缓存寿命为 10 秒，因此同一页面的下一轮通常需要新任务。`task-results.ts:14` 将查询入队，`job-runner.ts:43` 为每个任务创建新 Node 进程，`worker.ts:16` 无论读写都先打开整套 Site。每次查询还保留任务记录和日志文件。短任务的固定开销可能远大于查询本身；源码模式下空实时任务往返实测约 1.42 秒，正式编译版本的启动时间本次未测。

`job-runner.ts:14` 每 250 ms 检查一次队列，`:31` 起即使没有待执行任务，也用 immediate 事务查询运行数和队列。`storage.ts:92` 的任务表没有通用 status 索引，查询计划为 `SCAN jobs`。100,000 条完成记录时，一次空检查约 9.81 ms，按四次每秒计算，单这项就约 39 ms/秒同步工作，尚未计入其他轮询。写事务遇到其他写入时，还可能等待 `busy_timeout=5000`；这个等待上限来自配置，不是本次实测卡住五秒。

读报表应使用有边界的长期工作进程或读取服务，复用连接和模块初始化；持久发布、备份等写任务继续使用可靠队列。给队列状态补索引，空闲时避免无谓获取写锁，并设计查询任务与日志的保留/归档规则。只读轮询不应无限制造永久任务。不要仅把缓存时间拉长来掩盖这一结构性增长。

**8. P2：Newsletter 每个页面都重建全站展示数据。代码路径已确认。**

`apps/web/src/themes/Newsletter.astro:37` 起，每次渲染都生成全站 posts、查所有文章浏览量、排序 popular、计算 featured、分类数量和推荐内容，而文章正文页也执行同样的准备。`analytics.ts:219` 已使用增量 view_counts 并按 200 项批量查询，这是正确的；问题是调用方每页仍查询全部文章，并不是底层还在逐次扫描 events。3,000 篇会产生约 30 次浏览量批量 SQL 查询。

应根据首页、归档、搜索、文章页实际需要准备数据；静态内容索引按 releaseId 复用，热门排名按浏览计数变化或短时间窗口更新。只给展示项读取必要的媒体信息。把计数查询、推荐候选和排序结果与正文渲染分开，防止短生命周期的热门数据让整套内容缓存全部失效。本次未单独测量 Newsletter 的完整页面耗时，不能将默认主题的模板渲染数字直接套用到它。

**9. P2：内容正文、目录和图片属性在每次访问时重复派生。部分已测量。**

`packages/core/src/render.ts:220` 对没有区块的已发布文章重新调用 `renderDocument(entry.document)`，而发布对象已有 `html`。随后生成目录，Newsletter 对内容再次调用 `articleOutline()`。`media.ts:124` 对包含媒体的 HTML 再使用 Cheerio 解析，每张没有 srcset 的图片分别读取媒体记录。代码高亮、Markdown、安全清理和 HTML 解析都不是免费的。

建议按正文修订、模板/共享区依赖、渲染器版本缓存可以复用的片段与目录，并明确区分来源正文和最终模板页面，避免整页缓存错误包含登录态、实时计数或查询参数。纯文档正文先复用发布时的 HTML；区块与扩展正文按依赖指纹缓存。媒体属性使用批量查询或有失效机制的有界缓存。默认主题 3,000 篇下单次模板渲染中位数约 5.33 ms，远小于发布全站渲染，因此应在 P1 之后处理。

**10. P2：公开版本首次读取需要加载全部正文，内容对象复用没有等于内存复用。已实测。**

`packages/core/src/release-reader.ts:16` 对每个 entryKey 分别查询并解析完整对象；`site-releases.ts:20` 缓存完整公开版本，最多保留两个。3,000 篇时完整版本 JSON 约 27.9 MB，冷读约 98 ms。服务在新发布、版本切换或进程重启后会遇到这项同步开销；相邻版本即使绝大部分文章一样，也分别解析、持有对象。

建议拆分轻量公开目录与正文对象，按需加载正文；不可变对象按散列用有容量/字节上限的缓存复用。公开路由、ID、可见文章集合和导航也随版本准备好，减少每个请求重复计算。先避免主进程首次请求才同步解析整个版本，再考虑更细的预热策略。不能用无上限 Map 换取速度。

**11. P2：公开查询先取全量再分页，搜索也先物化全部命中。已实测，但当前规模尚属次要。**

`packages/core/src/query.ts:6` 的公开查询使用完整 release.entries 过滤、排序后切页；搜索又经 `publication-store.ts:74` 的 FTS 查询取全部命中，构造完整映射并再次经过列表筛选/排序。随着历史公开版本积累，搜索对象和成员关系也继续增长，需要同时观察实际查询计划，不能只测当前版的命中数。

本次 3,000 篇的普通分页约 2.96 ms，高频词搜索约 9.88 ms，没有达到秒级。可以为当前版本构建元数据索引，或利用现有公开成员表支持数据库筛选与分页，直接获取总数和本页结果；搜索查询要明确排序语义并控制返回量。现有后台 `entry_list` 已经是数据库分页，应该继续保留，不能把后台也改回全量读取。

**12. P2：后台初始依赖偏大，校验库的所有语言与不必要能力进入首屏。体积已分析。**

内存编译估算首次静态依赖 JS 约 831 KiB，其中 Zod 相关输入贡献约 453,921 字节；64 个语言文件贡献约 263,831 字节。Lexical 编辑器及世界地图没有进入首次静态依赖集合，已有懒加载确实生效。`App.tsx:16` 起仍提前引入类型、设置、运维和内容工作区，登录页与登录后的后台共用较大的依赖图。

可以分离登录入口与已登录工作区，将设置、类型和运维等按实际面板加载，收紧 contracts 的运行时导出边界及校验库的实际语言/功能依赖。继续保留接口契约校验，不应靠删除校验来减包。上述贡献是当前 esbuild 图中的字节归属，压缩后收益不能机械相加，也不能保证 Vite 会得到完全相同的数字；应在真正优化后再用正式构建对照验证。

**13. P3：每次输入反复复制和序列化整篇内容，本地草稿重写整个档案。核心开销已测量，浏览器影响待验证。**

`apps/admin/src/edit-session.ts:15` 每读一次 dirty 就 stringify 整个 value，change() 中还会读 dirty。`useEntryEditor.ts:183` 的 effect 在每次内容变化时立即 `saveLocalDraft()`，而 1,200 ms 延迟只作用于服务器保存。`local-drafts.ts:14` 起会读回全部草稿，克隆当前文章，反复序列化计算总大小，最后整体写回。`PageDesigner.tsx:17` 每次 render 也 stringify 整棵区块树，并在 650 ms 后保存并重新加载 iframe。

建议用明确的修改序号管理 dirty，保存时才生成需要的快照；恢复副本改为按文章保存并合并短时间连续修改，采用异步存储降低主线程同步写入。必须保留未保存提示、离开前处理、修订冲突和恢复语义。画布只因真正的数据变化更新，并继续合并预览请求。当前核心测量没有证明明显卡顿，因此此项不能排在已确认的秒级发布问题前面；后续需要用户允许浏览器测试后再核实长文和复杂区块的输入响应。

**14. P2：上传在进入工作进程前仍占用多份完整文件，并同步落盘。代码路径已确认。**

`apps/admin/src/Selectors.tsx:49` 和 `useContentWorkspace.ts` 使用 FileReader 读取完整 DataURL，再用 base64 JSON 上传。`packages/core/src/http-body.ts` 缓冲全部请求并解码字符串，`apps/web/src/api/media.ts:22` 解 base64 后调用 `stageMedia()`，该方法同步计算散列和 `writeFileSync()`。图片处理已在任务进程里，但接收阶段仍在网站主进程。一个 32 MiB 文件的 base64 本身约 42.7 MiB，尚未计入请求块、JSON 字符串、解码 Buffer 及浏览器副本；实际峰值本次未测。

应让文件以二进制流进入独立暂存目录，边接收边计算散列及核对大小，完整落盘后再创建处理任务。文件格式校验、幂等、进度和失败恢复继续共用同一协议。CLI 与浏览器上传都应走这个稳定入口。任务边界要包含接收后的重处理能力，避免仅把图片压缩放到子进程就认为整条上传链已经隔离。

**15. P3：备份、大文件导入与历史归档仍有整文件内存开销，冷启动也有不必要初始化。代码确认，极限规模待测。**

`packages/core/src/backup.ts:44` 和 `:65` 用 `digest(readFileSync(file))` 校验每个文件，单个大视频就要求同等大小的 Buffer。`history-archive.ts:39` 将 JSONL 整文件读入、切行并解析；`wordpress-wxr.ts:14` 虽然用 SAX，却把 XML 节点累积成完整树，调用方也先读完整 XML。WXR 上限 128 MiB 并不意味着转换后的对象树和候选内容能在 768 MiB 堆内稳定处理。本次没有测量接近这些上限的数据，也没有据此断言导入必定失败。

这些操作多数已有后台任务隔离，可以在保留格式和恢复能力的前提下改成分块散列、逐行归档读取和有界导入批次，复杂关联用临时索引完成。`code-blocks.ts` 还在模块载入时同步初始化所有内置高亮语言，而每个查询任务都会重新加载相应模块；可按需要初始化高亮器，优先让纯统计任务免于加载内容渲染模块。此次全量单元测试耗时约 87 秒，报告的 import 占比约 47%，说明启动成本值得单独看，但不能据此将全部时间都归因于 Shiki，也不建议为了缩短测试直接取消隔离。

优先完成第 1、2 项，共用同一发布执行模型，否则单独修改某个按钮会漏掉定时和计划入口。随后处理第 3 项主进程重扫描，以及第 4、5 项重复访问成本。这几项可以直接改善整站可用性和真实传输开销。

下一组处理统计计算与任务调度，即第 6、7 项；再利用共同的不可变内容目录和依赖索引完成第 8～11 项。第 12 项后台依赖和第 14 项上传可以独立推进。第 13、15 项按真实长文、大媒体和迁移数据的测量安排，不需要为尚未复现的场景更换整套架构。

这些是优化设计与排序，不是新增加的验收要求。本次没有设置未经确认的 QPS、首屏时间或内存达标线。下一步若实施优化，直接复用相同数据和测量方法比较前后结果，并保留已有的版本冲突、发布原子性、隐私可见性、恢复和导入一致性。

## 已有有效设计

访客页面不加载 React 管理后台和 Lexical；管理后台对编辑器、统计地图及多个面板采用懒加载。后台内容和媒体已有 SQL 分页与摘要索引。公开对象和全文索引按内容散列复用，避免每次发布在数据库重复复制整站正文。发布快照缓存有边界，媒体权限判断使用专门索引。媒体响应支持流式传输、Range 和 HEAD。访问总量使用增量计数表，统计报表有子进程隔离、请求合并及有界短期缓存，实时轮询在页面不可见时暂停。这些能力应保留并继续利用。
